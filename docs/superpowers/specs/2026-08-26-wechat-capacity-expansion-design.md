# 微信视频号采集容量扩展设计

## 目标

统一 wx_channel 批次协议与 TrendRadar 微信视频号目标的有效上限，避免配置页允许保存、运行时却因批次校验拒绝的问题。第一阶段目标上限为：

| 字段 | 目标上限 |
| --- | ---: |
| 采集作品数 | 30 |
| 每作品一级评论数 | 500 |
| 每条评论回复数 | 100 |
| 每作品回复总数 | 200 |

作品数和回复总数保持当前稳定值；本次只提高一级评论数和单评论回复数。

## 方案与边界

- ltaoo 接口和页面桥不改，继续使用现有评论、回复分页及 marker 处理。
- wx_channel 批次请求校验、默认值、边界测试与结果截断语义统一到上述上限。
- TrendRadar 的微信视频号容量合同、采集器校验和管理页面字段上限统一到上述上限。
- 其它平台的通用上限不随本次变更调整；平台容量仍由各自容量合同校验。
- 回复采集仍要求两个回复上限同时为 0（关闭）或同时大于 0（启用）。

## 运行语义

采集器按现有分页循环继续请求，达到目标上限后停止，并在结果中保留截断标记和安全原因。重复 marker、无新增数据、关系不完整等现有安全停止规则保持不变。扩大上限不改变部分完成和幂等入库语义。

关键字模式和分享链接模式仍保持二选一，不在本次容量扩展中引入混合采集。

## 兼容性

- 旧批次请求使用较小 limits 时继续有效。
- 新上限只影响微信视频号批次，其他平台和旧 schema 字段不变。
- TrendRadar 在发送批次前校验相同的上限，避免把必然失败的请求交给运行时。

## 验证计划

1. wx_channel 单元测试覆盖 500 条一级评论、100 条单评论回复、200 条作品回复的边界接受和超限拒绝。
2. wx_channel 分页 fixture 覆盖达到上限时停止、重复 marker 和截断回执。
3. TrendRadar 配置、容量合同、采集器和管理页面测试覆盖相同上限及旧值兼容。
4. 两个仓库的相关回归测试全部通过后，使用受控批次验证较大 limits 的结果 schema、部分完成状态和清理回执。
5. 在真实 PC 微信环境中再决定是否进行大评论量压力验收，不把 fixture 结果表述为真实容量证明。

## 风险与回滚

容量提高会增加请求数、运行时间和本地存储占用。运行时保留现有超时、marker 安全停止和清理回执；若真实验收出现不稳定，可将 TrendRadar 配置上限回退到旧值，旧批次仍可继续运行。
