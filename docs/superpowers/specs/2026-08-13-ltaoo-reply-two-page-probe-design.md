# ltaoo 回复两页可行性探针设计

## 1. 目标

在不接入完整采集器的前提下，验证已经通过一级评论两页测试的 ltaoo 页面/代理链路能否：

1. 从一级评论第一页识别一个仍有未展开回复的有效根评论；
2. 获取该根评论的回复第一页；
3. 在存在非空回复游标时，仅执行一次回复翻页；
4. 证明第二次回复请求使用了第一页返回的原始游标；
5. 观察内嵌回复、独立回复页和跨页回复之间的重复与父子关系语义。

本阶段只验证一个作品、一个根评论和最多两页回复。它不扫描第二个根评论，不请求一级评论第二页，不遍历完整列表，也不接入完整 POC 采集器。

## 2. 前置事实

- ltaoo 旧提交 `c0c2b8cc36af52ab2c3eb50cb7dc08b7d963efb0` 已在真实环境中成功解析同一作品并获取两页一级评论。
- 该旧版 `/api/status` 的 `channels.available` 不可信；现有探针已通过共享页面 profile 作为旧版页面 WebSocket 的最终就绪证明。
- 已合并的 POC 代码把 `levelTwoComment` 作为内嵌回复，把 `expandCommentCount` 大于内嵌回复数的一级评论加入独立回复分页队列，并用 `comment_id` 和 `next_marker` 请求回复。
- POC 已有完整分页、去重、重复游标和中断恢复逻辑，但这些能力不在本次真实探针中启用。

## 3. 方案选择

新增独立脚本 `scripts/probe-ltaoo-replies.ps1`，复用现有运行 manifest、回环 API 限制、状态适配语义、脱敏方法和清理脚本。

不采用以下方案：

- 给 `probe-ltaoo-comments.ps1` 增加模式参数：会把已经稳定的一级两页探针与新回复行为耦合。
- 直接运行完整 POC：请求量、数据范围、检查点和失败面超过本阶段目标。

新脚本将结果写入同一运行目录中的 `reply-probe-summary.json`，不覆盖 `probe-summary.json`。

## 4. 安全边界

- API 基址只允许 `http://127.0.0.1:<port>`。
- 状态请求最多一次，profile 请求最多一次。
- 评论接口请求最多三次：一级第一页一次，回复请求最多两次。
- 不自动重试，不请求一级第二页，不请求第二个根评论，不请求回复第三页。
- 分享链接、`oid/nid`、根评论 ID、回复 ID 和原始游标只存在于进程内存。
- 不保存或输出正文、昵称、账号、头像 URL、原始响应、Cookie、请求头或代理凭据。
- 随机盐只存在于本次探针进程内存；所有评论 ID 和游标只保存带盐 SHA-256。
- 复用现有临时 CA、ltaoo 进程身份校验和清理脚本，不扩大证书、系统代理、TUN、路由或 Clash 权限。
- 自动测试只使用回环 HTTP fixture，不启动真实 ltaoo，不安装 CA，不修改 Clash。

## 5. 根评论选择

一级第一页只从 `data.data.commentInfo` 读取。对每个一级评论按源顺序检查：

1. `commentId` 必须是非空字符串；
2. `levelTwoComment` 中能解析为对象的元素计为内嵌回复；
3. `expandCommentCount` 必须是非负整数；
4. `expandCommentCount` 必须大于内嵌回复数。

选择第一个满足全部条件的评论作为唯一根评论。不得因为后面的评论回复更多而改变选择顺序，也不得输出其原始 ID。

若没有合格根评论，立即输出 `inconclusive_no_eligible_root`。此时评论接口请求总数必须为一次，回复请求数为零。

## 6. 请求流程

1. 校验运行 manifest 和回环 API 基址。
2. 调用 `/api/status`，使用已批准的新旧状态规范化规则。
3. 调用共享页面 profile，取得只在内存中使用的 `oid/nid`。
4. 调用一级评论第一页：`/api/channels/feed/comment/list?oid=...&nid=...`。
5. 按第 5 节选择唯一根评论。
6. 请求回复第一页，查询参数包含 `oid`、`nid` 和 `comment_id`，不传 `next_marker`。
7. 若回复第一页 `lastBuffer` 为空，停止并输出 `inconclusive_no_second_reply_page`。
8. 若游标非空，使用原始值经标准 URL 编码构造唯一一次回复第二页请求。
9. 第二页成功后立即停止，不使用第二页返回的游标继续请求。

每个请求超时 30 秒。各类请求计数在对应请求发出前立即递增，确保超时或传输失败的摘要仍能反映实际尝试数量。

## 7. 去重与关系观察

> 本节原始的“两字段均等于根评论”规则已由 `docs/superpowers/specs/2026-08-13-ltaoo-reply-relation-semantics-design.md` 修订；实现与验收以修订规格为准。

探针在内存中维护以下集合：

- 选定根评论的内嵌回复 ID；
- 回复第一页 ID；
- 回复第二页 ID；
- 所有已经观察到的回复 ID。

有 ID 的回复按原始 ID 计算页内重复、跨回复页重复，以及内嵌回复与独立回复页的重复。无 ID 回复只计入数量和缺失 ID 数，不生成替代 ID，也不参与跨页去重。

对独立回复页中的每条回复检查源响应明确提供的 `replyCommentId` 和 `rootCommentId`：

- 非空且不为 `"0"` 的值必须等于选定根评论 ID；
- 显式匹配、字段缺失/`"0"` 和显式冲突分别计数；
- 任一显式冲突立即以 `reply_relation_mismatch` 失败；
- 字段缺失只记录为能力缺口，不推断父 ID，也不把请求上下文冒充源字段。

## 8. 脱敏摘要

`reply-probe-summary.json` 只允许包含：

- `schema_version`、`run_id`、完成时间；
- 分享链接和 `oid/nid` 的 SHA-256；
- `status_schema`、`readiness_proof`；
- HTTP 状态和业务码；
- 一级、回复及评论接口请求计数；
- 一级评论数、合格根评论是否存在、内嵌和独立回复数量；
- 根评论及回复 ID 的带盐哈希；
- 页内、跨页、内嵌与独立页重复计数；
- 缺失回复 ID 数；
- 父/根关系的匹配、缺失和冲突计数；
- 回复游标是否存在、长度、带盐哈希、第二次请求游标哈希和连续性；
- 最终状态和稳定原因码。

摘要和终端输出不得包含任何原始敏感值或模拟 fixture 中的诱饵秘密。

## 9. 结果状态

### `verified_reply_two_pages`

必须同时满足：

- 一级第一页和 profile 成功；
- 找到唯一选定的合格根评论；
- 回复第一页和第二页 HTTP、业务响应成功；
- 第二次回复请求游标哈希等于第一页响应游标哈希；
- 回复请求数精确为两次，评论接口总请求数精确为三次；
- 没有显式父/根关系冲突或敏感数据泄漏。

### `inconclusive_no_eligible_root`

一级第一页成功，但没有合格根评论。该结果只说明样本不适合验证回复接口，不表示回复采集不可行。

### `inconclusive_no_second_reply_page`

回复第一页成功，但 `lastBuffer` 为空。该结果证明单页回复接口可用，但不能证明回复翻页可用。

### `failed`

包括状态/profile、一级第一页、回复请求、响应结构、游标连续性、安全边界或显式父子关系失败。失败后不得发送新的评论请求。

## 10. 自动测试

Windows Go 测试使用 `httptest.Server` 驱动 PowerShell 脚本，覆盖：

1. 跳过无 ID、回复已全部内嵌或计数字段无效的评论，选择首个合格根评论。
2. 一级一次加回复两次，总评论请求数精确为三次。
3. 包含 `+`、`/`、`=` 的回复游标原样进入第二次请求。
4. 无合格根评论时只发一级一次请求。
5. 回复第一页无游标时不请求第二页。
6. 内嵌回复与独立页重复、回复页内重复和跨页重复均正确计数。
7. 显式父/根关系匹配、缺失和冲突语义正确；冲突立即失败。
8. profile 失败前评论请求为零，一级失败前回复请求为零。
9. 未知状态结构、远程 API 基址和超过请求上限的代码路径被拒绝。
10. 摘要和终端不泄漏链接、正文、昵称、账号、原始 ID、原始游标或诱饵秘密。
11. 新脚本通过 Windows PowerShell 5.1 语法解析。
12. 现有一级探针、准备和清理测试继续通过。

## 11. 真实验收顺序

1. 从审计过的固定旧提交重新构建 ltaoo Windows EXE并记录提交与 SHA-256。
2. 运行现有准备脚本，确认基线、临时 CA 指纹、API 和代理端点。
3. 以可回滚方式临时配置 Clash，并确认 ltaoo 进程直连、目标流量进入 `127.0.0.1:2023`。
4. 打开或刷新一个公开回复数量足够的目标页面。
5. 分享链接只从剪贴板读取到内存，不打印、不写日志。
6. 运行回复探针一次。
7. 无论成功、不确定或失败，先恢复 Clash，再清空剪贴板并运行现有清理脚本。
8. 独立审计 CA、私钥、配置、进程、端口、Clash 规则和备份均无残留。

## 12. 验收标准与后续

- `verified_reply_two_pages`：允许进入下一独立阶段，验证异常/重复游标停止语义。
- `inconclusive_no_eligible_root` 或 `inconclusive_no_second_reply_page`：清理后更换回复更多的公开样本，以新 `run_id` 重试，不扩大请求范围。
- `failed`：按稳定原因码诊断，在根因明确前不运行完整采集器。

只有回复两页、异常游标、去重和长列表中断四个独立切片均通过后，才讨论把 ltaoo 适配器接入完整 POC。
